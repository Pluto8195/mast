# Workflow assumptions: audit and design

2026-11-03 · audited against `d40adecf8` (`origin/work-outline-implementation`). Audit/design only; no running app, private stores, builds, tests, or network service calls. This is a source audit, not proof of behavior in a real installation. Personal instructions in Mikey's live registry and installed skills were deliberately not inspected; export must preview the actual values locally. Line references below are relative to the Mast repository.

Classification: **A** neutral mechanics, keep; **B** setting, neutral new-user default and preserve existing effective behavior; **C** user-editable content; **D** remove. A classification is a recommendation, not a claim that every observed behavior is wrong. Ranked roughly by constraint on a coworker.

## Findings

1. **C — Universal MCP instructions prescribe a workflow.** `crates/mcp/src/jsonrpc.rs:27` tells every connected agent to bind worktrees, raise Required Actions for blocked decisions, publish every file, read a plan on every item chat, coordinate children, poll for “Ready to merge”, and archive workers. Some are useful feature mechanics, but mandatory planning, reporting and coordination are a process. Keep concise conditional capability and safety guidance in the server; move imperatives into opt-in Space/item instructions. In particular, do not silently change the existing instructions payload's provenance/hash contract. Existing users get the exact old behavioral text as an editable, ordered instruction at the equivalent scope, with duplicate injection avoided. Mechanics such as scoped access, idempotency, honest attribution and sandbox limits remain A.
2. **C — Tool descriptions reinforce the same process.** `crates/mcp/src/tools.rs:140`, `:185`, `:224`, `:261`, `:313`, `:428`, `:479` instruct agents to archive, report, poll and publish; `crates/proto/src/agent.rs:1162` supplies “finish with Ready to merge” as an example. Replace imperatives with conditional descriptions of actual effects, reach and errors. Move coordinator roles, finish criteria, talk style and any personal worktree instructions into editable instructions/snippets. No generic code evidence found for a hard-coded talk-to-me skill; the current chat's Work Outline instructions and repository handoff are themselves personal content, not a universal binary prompt.
3. **B/C — “Ready to merge” has hidden product semantics.** `crates/ui/src/status_light.rs:15`, `:77`; `crates/ui/src/team.rs:297`; `crates/ui/src/work_outline/required_actions.rs:221`; `crates/engine/src/archivable.rs:26`, `:117` parse free text to change light, grouping and archive eligibility. Neutral default: ordinary requests are needs-attention; no text implies completion. Prefer an explicit optional action kind rather than user-configured magic strings. Migrate existing requests and Mikey's convention without changing their display or archive verdict; retain legacy matching only for migrated profiles until converted. A PR dashboard's actual “Ready to merge” label (`crates/proto/src/pr_dash.rs:87`) is a different, legitimate PR state.
4. **B — Wakes start agent turns by default.** `crates/proto/src/orchestrator_wakes.rs:43` and `:63` default on for actions, errors and worker reports, off for turn completion and PRs. `crates/engine/src/orchestrator_wakes.rs:11` batches, and `:478` routes reports through that queue. New profiles: orchestration and automatic wakes off; explicitly opt in per chat with event choices. Preserve all current effective per-chat values, including absent fields resolved through the old defaults, before changing defaults. Retain held/draft/idle guards. Disabling reports currently produces an error rather than a different delivery path (`crates/mcp/src/tools.rs:185`); expose this before a worker is instructed to report, and allow manual collection.
5. **B — Archiving encodes a specific definition of finished.** `crates/engine/src/archivable.rs:23`, `:87` accepts completed item, all linked PRs closed/merged, or resolved magic phrase; idle >3 days applies only with completed or archived item, and the completed branch already returns earlier. This is an eligibility rule for worker/bulk archive, not a global automatic deletion after three days. New default: manual archive, no inferred finished status; optional per-Space rules with preview and reasons. Migrate current rule exactly, including the actual archived-item 3-day case, rather than promising a blanket timer. Keep queued/input/open-action safeguards and explicit force audit.
6. **B — Model/harness selection can override the user's CLI and installed tools.** `crates/proto/src/agent.rs:33` forces Claude Opus 5.5 for missing Claude model; `crates/mcp/src/tools.rs:150`, `crates/engine/src/pr_review_launch.rs:544`, `crates/engine/src/work_outline_launch.rs:1155`, `crates/ui/src/pickers.rs:1093` show differing launch and remembered-pick paths. PR fallback explicitly picks Claude; a Codex-only user can hit an unavailable harness. New default: remembered or user-selected available harness, then harness's own default model; ask when ambiguous/unavailable, never silently select an expensive model. Provide profile defaults and per-action overrides for ordinary, item, PR and child launches, with clear inheritance. Migration must materialize the *old resolved effective value* per applicable path, including Opus for implicit Claude and PR fallback, while retaining explicit chat/model picks. Check CLI builder too so `None` truly means harness default.
7. **C/B — PR launcher copies a specific workspace and skill flow.** `crates/engine/src/pr_review_launch.rs:15`, `:302`, `:350`, `:485`, `:514` select/reuse checkout, may change a clean `main` checkout or create a worktree, assume a `.devcontainer` implies `/workspace/.worktrees`, and inject `/code-review` or `/fix-ci`. Those commands may not exist; the mount inference may be false. New default: editable generic review prompt without a skill dependency, show proposed checkout action and offer read-only remote diff/no checkout; never infer container mount from directory presence. Per-Space checkout strategy and prompt snippets reproduce Mikey's existing flow. Preserve consent and existing chat behavior on upgrade. `crates/ui/src/pr_review_launch.rs:109` is only a preview; verify actual generated prompt and editing flow in implementation.
8. **B — Worktree placement and branch assumptions leak across features.** `crates/proto/src/work_outline_launch.rs:54` defines a superproject `.worktrees/<label>/<slug>` layout; `crates/ui/src/overview.rs:699` recognizes worktrees by pathname; `crates/engine/src/diff_targets/refs.rs:20` falls back to `origin/main`; `crates/engine/src/pr_review_launch.rs:17` special-cases main. Use Git's actual worktree identity, configurable creation root/layout, and detected remote default branch (or ask, no fabricated base). A single checkout must be supported. Preserve existing layout and fallback as explicit legacy preferences where needed, not hard-coded `/Users/mikey` paths.
9. **B/C — Worker destination can create items as a side effect.** `crates/mcp/src/tools.rs:140`, `:1224` turn an omitted `workItemId` into a new item when a project has a destination. This is enabled by explicitly configuring the destination, but omission is not an obvious request to create an item. Make routing explicit in `create_chat` and describe its side effects; neutral omitted behavior inherits the current item, and configured automatic routing is opt-in. Migrate projects with a destination to the legacy routing setting, and retain idempotency and scoped authorization. Project templates are user-created (`docs/plans/work-outline/m0-contract.md`, amendment “project templates”); they do not mandate Tickets.
10. **B — Team UI makes orchestration a prominent fixed concept.** `crates/ui/src/shell.rs:615` calls it sticky; `crates/ui/src/team.rs:248` calculates worker facts and `crates/ui/src/shell/chat_item_ui.rs:955` shows a roll-up when nonempty. Add hide/auto/show and neutral “auto” that appears when used; preserve Mikey's sticky layout. Coordinator/child and admin features themselves are opt-in capabilities, not required organizational roles. Keep access discoverable in menus and empty states.
11. **B — Compact rows change the mental model of items and chats.** `crates/ui/src/work_outline/outline_view.rs:578` defaults `compact_single_chat` true; `crates/ui/src/work_outline/model.rs:661` combines rows. The setter exists, but the reviewed code does not establish a persisted user control. Offer compact/separate choice, default separate for clarity; persist true for existing profiles. PR/Linear icon-only compact presentation also merits density/labels choices (`crates/ui/src/github/row_icons.rs`); don't assume hover is sufficient.
12. **B — Notification and presence defaults are intrusive for some.** `crates/ui/src/settings.rs:665`, `:804` already expose per-event sounds, banners, live icon and menu bar, all enabled by default (banner background-only). New profile: sounds off, menu bar off, banner opt-in, static icon; preserve existing effective flags per device, even when omitted in an older settings file. Existing controls are A; improve first-run discoverability. Don't equate a new default with changing notification permissions.
13. **B — Keybindings are only partly configurable.** `crates/ui/src/settings.rs:694`, `crates/ui/src/shell/work_outline_ui.rs:348` use a persisted keymap for commands, but `:406` binds outline navigation from a fixed table, and `crates/ui/src/shell.rs:139`, `:476` hard-code Team shortcut. Extend the existing keymap and conflict detection to navigation, Team and other fixed contextual bindings; allow unbind, preserve scope and accessible defaults. Migrate old fixed combos into explicit settings; do not claim all shortcuts are currently rebindable.
14. **B — Admin grant duration is a fixed preference, not a required role.** `crates/ui/src/admin.rs:32` defaults to four hours with 1/4/8/24/until-revoked choices. Ask for duration or remember a user's last explicit choice; retain four hours for existing profiles. Never export grants, credentials, bypass flags or active permissions; keep per-call scope checks and bulk confirmation (A). `crates/engine/src/admin.rs:298` and `crates/mcp/src/tools.rs:1902` literally attribute grants/messages to Mikey: D, replace with truthful “the user” or actual grantor without fabricating identity. Similar personal tool wording at `crates/mcp/src/tools.rs:224`, `:428` should be removed.
15. **A/B — Linear is opt-in, but an opt-in sync has automatic effects.** `crates/proto/src/work_outline.rs:452` defaults Linear off; `:458` and `:463` hold explicitly chosen destinations. `crates/engine/src/linear/assigned.rs:217` skips absent destination but creates/archives local items on sync once set. New users should see manual linking by default and a clear preview of ongoing local create/archive behavior before enabling assigned sync. Preserve configured destinations and sync behavior for existing users. No Linear writes are implied. The handoff's original “manual only” describes v1, not the later assigned-sync feature.

## Remaining inventory and boundaries

- **A/C — Instructions and launch.** Effective Space/ancestor/item instructions are user-authored, ordered and provenance-bearing; delivery is the feature, not a personal prompt. `crates/engine/src/work_outline_launch.rs:347`, `:754`, `:1155` sends the visible user prompt plus the chosen revision; no evidence there of an additional “finish with” launch prompt. Empty instruction sets permit unsupported harnesses, but with instructions `:770` refuses unsupported harnesses; `crates/engine/src/instruction_delivery.rs:215` supports Claude and Codex. Explain this limitation rather than silently dropping instructions. Preserve revision pins, priority and audit trail.
- **A/C — Wakes and reports.** System-attributed worker update text is generated by Mast (`crates/engine/src/orchestrator_wakes.rs:529`), with batching/hold semantics (A). The instruction to report and the expected report style belong in user content (C). If disabled, user can still read child results; do not present this as equivalent to an automatic report.
- **A/B — Templates and admin.** Container rules are explicitly configured and propagate to following children; applying to moved items is explicit (`docs/plans/work-outline/m0-contract.md`, amendment “container templates”). Copy templates are optional, not a built-in copy of Mikey's structure. Make propagation and inherited instruction edit/mute semantics obvious. Admin grants are explicit and scoped, not on by default. Workflow packs should compose these mechanisms, not create a parallel authority system.
- **A/B — No-outline use.** `crates/mcp/src/tools.rs:256` explicitly permits no associated item, and `crates/ui/src/shell/start_chat_ui.rs:5` describes a normal prompt; however global MCP instructions still steer unassociated chats toward artifact and worktree conventions. Neutral conditional guidance plus a normal chat-first entry point is required. Verify full first-run and no-item flows headlessly before claiming parity. Codex-only: see finding 6; no Linear: see 15; no worktree: see 7–8; no orchestration: see 1–5 and 10.
- **A/B — Identity and repositories.** The runtime literal search found Mikey in attribution and descriptions above. `/Users/mikey`, Cofactr repository URLs and login occur mainly in fixtures, comments and project docs, e.g. `crates/engine/src/repos.rs:2281`, `crates/engine/src/pr_chat_links.rs:534`; they are not evidence of configured production paths or orgs. `crates/engine/src/pr_ticket_cache.rs:1038` explicitly documents avoiding a fixed Cofactr owner. HANDOFF paths, `Pluto8195`, integration branch, backups, Space names and release rules are Mast-development instructions (`docs/plans/work-outline/HANDOFF.md`), not shipped defaults; keep them project-local. No personal email or fixed Linear team was established in runtime source by this audit. Keep searching generated assets and launch paths before declaring the inventory exhaustive.
- **A — Theme versus brand.** The Mast mark uses the Cofactr palette (`docs/plans/work-outline/HANDOFF.md`, “Renamed to Mast”), but the app already has theme selection, custom themes and imports (`crates/ui/src/settings/appearance.rs:14`, `:911`). Do not claim Cofactr is the only app theme. Branding is product design; expose optional accent/logo customization only if desired, retain current look for Mikey.
- **B — Other branch assumptions.** New repo initialization uses `main` (`crates/engine/src/repos.rs:493`); PR dashboard has a candidate list (`crates/engine/src/pr_dash.rs:62`); artifact drift excludes branch names (`crates/engine/src/artifacts.rs:1441`). Detect actual default branch where practical; let user select, and preserve existing behavior until migrated. Tests and examples naming `main` or Cofactr are not runtime policy.

## Migration: preserve existing behavior before changing defaults

Use a versioned, idempotent per-profile migration plus device-local migration for UI/wake data. Determine existing versus new using an existing durable profile/schema marker, not machine name or identity. Snapshot **effective old values**, including omitted serde defaults, for every profile, Space and relevant chat before switching defaults. Do not overwrite explicit values, live grants, instruction revisions or other devices' preferences; sync profile/Space settings via their existing ownership rules, and migrate device-local stores on each device. Transaction/backup and marker must be atomic or safely retryable; preserve unknown fields, support rollback, and do not create duplicate instructions on retry. For running sessions, preserve their pinned instructions until next authorized revision/session transition. New installs receive neutral defaults only. Provide a settings diff/undo and tests for missing fields, partially migrated data, old clients, multi-device conflicts, existing explicit choices, replay and upgrades from old versions. Verify Mikey's actual effective settings with his consent on his device; this audit did not read them and cannot assert their values beyond code defaults and handoff.

## Optional workflow pack

Call it **Workflow pack**: a versioned, inspectable local export of selected existing settings and content, not executable code or a new policy authority. Export selected Space/item instruction text with ordering and source labels; project copy templates and container-template rules using their existing representations; optional prompt snippets, wake/event defaults, launch/model/harness choices, archive rules, density, notifications and keymap. References to skills are names/descriptions only, not copied executable skills. Exclude chats, transcripts, tokens, accounts, active grants, secrets, repository paths and identifiers by default; warn and allow editing of any free text that may contain private information. Never automatically export personal data.

Import opens a preview showing every instruction, setting, template, potential propagation, unresolved skill/model/repo references and conflicts. Choose individual sections and destination Space/container; map roots and external references explicitly. Default all changes unchecked, no automatic skill installation, no model substitution, no grant or sync activation. Apply through existing instruction/provenance and template mutations; use admin chat bulk preview/Required Action only when the user explicitly delegates, otherwise ordinary user actions. Existing instructions remain separately attributed, not flattened; preserve template copy versus live-follow semantics. Show diff, limits and failures before apply; provide a change receipt and undo where supported, clearly identify operations that existing undo cannot reverse. Version schema, validate size and unknown fields, reject unsupported versions safely, and make re-import idempotent with explicit replace/keep/duplicate choices. A pack is optional and does nothing until reviewed and applied; Mikey can export his migrated setup, and a coworker can adopt only the parts they want. Start with local file export/import and no sharing service.

## Small mergeable phases

1. **Preservation foundation:** introduce explicit legacy-effective settings and versioned migration with no behavioral changes for existing users; add provenance-aware editable legacy prompt content and migration tests, keeping effective injected text identical. No new-user default changes until verified. Inventory actual implicit defaults on each launch path.
2. **Neutral agent guidance:** make MCP text conditional and tool descriptions factual; move coordinator/report/plan conventions to the migrated editable content; neutralize personal attribution. Test delivered prompt order, revision pins and absent-outline behavior. Preserve Mikey's resulting instructions and messages.
3. **Launch choices:** unify per-action harness/model defaults; editable PR prompts and explicit checkout strategy, real Git identity/default-branch detection. Test Codex-only, missing skill, single checkout and non-main repositories. Preserve legacy launch choices.
4. **Opt-in orchestration:** wake/event defaults, explicit child routing and archive rules; replace magic phrase with explicit action kind and migrate old requests. Preserve current wake delivery, status and archive verdict for migrated profiles; no silent background turns on fresh profiles.
5. **Interface preferences:** Team visibility, density, full keymap coverage, notification/menu defaults, admin duration and clearer Linear sync preview. Preserve effective UI settings per device.
6. **Workflow pack:** export/preview/selective import atop the above settings, instructions and templates. Exercise redaction, conflict handling, authorization, partial failure and round trips; no service or executable pack contents.

Each phase can ship independently with old/new profile tests, migration replay and rollback checks, and targeted headless coverage. User acceptance should include Mikey comparing his current workflow after upgrade and a fresh coworker completing a normal Codex-only chat in one repository with no outline, Linear, worktrees or orchestration.
